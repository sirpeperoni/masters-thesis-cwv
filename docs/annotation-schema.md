# Аннотационная схема набора данных «коммит → изменение Core Web Vitals»

Документ описывает, что и как размечается в наборе данных диссертации, в каких форматах хранятся
аннотации и как проверяется их качество. Файлы аннотаций — в папке [`annotations/`](../annotations/),
инструмент — [`ml/annotation.py`](../ml/annotation.py).

**Объект разметки** — пара версий фронтенд-приложения «база → коммит»: что изменилось в коде и как
это изменение повлияло на метрики производительности Core Web Vitals (LCP, INP, CLS) и TBT.

Разметка ведётся в два слоя:

- **автоматический** — получается программно: статистическая метка регрессии по замерам, выбросы
  в прогонах, шаблоны кода в изменённых строках, предварительная категория LCP-элемента;
- **ручной** — делают аннотаторы: ожидание регрессии по diff (вслепую), тип и категория изменения,
  файл-причина регрессии, проверка категории LCP-элемента.

---

## Шаг 1. Состав аннотационной схемы

### 1.1. Модальности

| Модальность | Данные | Почему включена |
|---|---|---|
| **Замеры** (последовательности прогонов) | JSON: прогоны Lighthouse базы и коммита — числа во времени, как сигнал | на них строится целевая переменная — метка регрессии |
| **Текст: изменение кода** | diff «база → коммит», сообщение коммита | по нему модель прогнозирует регрессию; это основной неструктурированный вход |
| **Текст: страница** | элемент, по которому посчитан LCP: селектор, видимый текст, фрагмент HTML | показывает, *что именно* измерено как «основное содержимое» |

**Изображения и аудио не включены.** Скриншоты страниц в стенде отключены (`disableFullPageScreenshot`):
они замедляют прогон Lighthouse и не нужны для метрик. Аудио в данных нет (звуковые файлы monkeytype
встречаются только как изменённые файлы в diff и размечаются как файлы, а не как аудио).

### 1.2. Сущности по модальностям

| Модальность | Сущности и явления, которые размечаются |
|---|---|
| Замеры | пара версий; изменение метрики (регрессия, улучшение, без изменений); отдельный прогон (обычный, выброс, ошибка) |
| Текст: изменение кода | коммит (тип, ожидание регрессии); изменённый файл или фрагмент (категория влияния, причина регрессии); строка кода с шаблоном, важным для производительности |
| Текст: страница | страница; LCP-элемент (категория: основной контент, логотип, баннер, окно согласия…); его атрибуты |

### 1.3. Сводная таблица (модальности × группы объектов)

| Модальность | Объект целиком | Часть объекта | Наименьшая единица |
|---|---|---|---|
| Замеры | пара «база → коммит»: итоговая метка | метрика: Δ, p, q, метка | прогон: значения, статус, LCP-элемент |
| Текст: изменение кода | коммит: тип, ожидание регрессии, ожидаемые метрики | файл: причина или нет, категория влияния, метрика | строка: шаблон кода (обработчик, таймер, импорт…) |
| Текст: страница | страница проекта | LCP-элемент: категория, основной ли это контент | атрибуты: селектор, текст, тег |

## Шаг 2. Требования к аннотациям

### 2.1. Типы сущностей и атрибуты

**Замеры**

- *Пара* — `label` ∈ {`regression`, `improvement`, `none`}; атрибуты: `status`, `aa`, `self_aa`, `extended`.
- *Метрика* (`lcp`, `inp`, `tbt`, `tbtFlow`, `cls`, `lcpObs`) — `<m>_label` ∈ {`regression`, `improvement`, `none`};
  атрибуты: медианы `<m>_base`, `<m>_head`, разность `<m>_delta`, `<m>_rel`, `<m>_p`, `<m>_q`.
- *Прогон* — `status` ∈ {`ok`, `outlier`, `error`}; атрибуты: значения метрик, `outlier_metrics`, `lcp_element_id`.

**Текст: изменение кода**

- *Коммит* — `expect_regression` ∈ {`yes`, `no`, `unsure`}; атрибуты: `expected_metrics` (подмножество
  `lcp;inp;cls;tbt`), `change_type`, `perf_category`, `comment`.
- *Файл* (только у регрессий) — `is_cause` ∈ {`yes`, `no`, `unsure`}; атрибуты: `perf_category`, `effect_metric`.
- *Строка* — `pattern` (имя шаблона); атрибуты: файл, номер строки, `+`/`−`, текст.

**Текст: страница**

- *LCP-элемент* — `manual_category`; атрибуты: `is_page_content` ∈ {`yes`, `no`}, `auto_correct`, `comment`.

### 2.2. Согласованность: единые словари

Одни и те же словари используются во всех модальностях и на всех уровнях: категория влияния
коммита (уровень 1) и файла (уровень 2) берутся из одного списка; метрики везде называются одинаково.

**Категория влияния на производительность** (`perf_category`):

| Значение | Что относится | Типичная метрика |
|---|---|---|
| `dependency` | добавление, удаление, обновление пакетов | LCP, TBT |
| `bundle` | рост или перестройка сборки, крупный новый модуль в основном бандле | LCP |
| `render_blocking` | скрипты, стили, шрифты, блокирующие первую отрисовку (`<head>`, preload, inline-скрипты) | LCP |
| `main_thread` | тяжёлые вычисления, циклы, синхронная инициализация | TBT, INP |
| `event_handler` | обработчики ввода и событий | INP |
| `timer_animation` | таймеры, requestAnimationFrame, анимации на JS | TBT, INP |
| `dom_layout` | чтение размеров и запись в DOM, принудительный пересчёт вёрстки | INP, CLS |
| `css` | стили, раскладка, CSS-анимации, тяжёлые селекторы, смена CSS-фреймворка | LCP, CLS |
| `media` | изображения и видео, их размеры | LCP, CLS |
| `font` | шрифты, их загрузка и подмножества | LCP, CLS |
| `code_splitting` | ленивая загрузка, динамический импорт | LCP (обычно улучшение) |
| `framework` | миграция или смена подхода фреймворка (руны Svelte 5, переход на Solid) | TBT, INP |
| `content` | тексты, переводы, баннеры с содержимым | LCP (смена LCP-элемента) |
| `third_party` | сторонние скрипты: реклама, аналитика, мониторинг | TBT, LCP |
| `none` | не влияет на производительность | — |

**Тип изменения** (`change_type`): `feature`, `fix`, `refactor`, `dependency`, `build`, `style`,
`content`, `test_docs`, `perf`.

**Категория LCP-элемента** (`manual_category`): `main_text`, `main_image` (основной контент страницы),
`logo`, `navigation`, `footer_hint`, `banner`, `consent_modal`, `error_message`, `placeholder`, `other`.

## Шаг 3. Формальные и содержательные требования

### 3.1. Форматы и структуры

| Модальность | Файл | Формат | Ключ связи |
|---|---|---|---|
| Замеры, уровни 1–2 | `data/<проект>.labels.csv` | CSV, UTF-8, строка на пару | `sha` |
| Замеры, уровень 3 | `annotations/measurements/<проект>.runs.csv` | CSV, строка на прогон | `sha` + `side` + `run` |
| Текст кода, уровень 1 | `annotations/text-diff/pilot-phase1.<аннотатор>.csv` | CSV, строка на пару | `id` → `pilot-key.csv` → `sha` |
| Текст кода, уровень 2 | `annotations/text-diff/pilot-phase2.<аннотатор>.csv` | CSV, строка на файл | `id` + `file` |
| Текст кода, уровень 3 | `annotations/text-diff/pilot-patterns.auto.jsonl` | JSONL, строка на шаблон (аналог CoNLL-U: «единица — строка, атрибуты — поля») | `id` + `file` + `line` |
| Текст страницы | `annotations/text-page/lcp-elements[.<аннотатор>].csv` | CSV, строка на уникальный элемент | `element_id` |

Пример записи уровня 3 текста:

```json
{"id": "P48", "sha": "b3c8bd6c…", "file": "src/lib/components/History/historyState.svelte.ts",
 "side": "+", "line": 201, "pattern": "timer", "text": "autoSaveTimer = setInterval("}
```

Требования к файлам: кодировка UTF-8; разделитель CSV — запятая; несколько значений в одной ячейке —
через `;` без пробелов (`lcp;tbt`); пустая ячейка — «не размечено»; значения категорий — строго из
словарей шага 2.

### 3.2. Содержательные требования

- **Слепота фазы 1.** Аннотатор оценивает коммит только по diff и сообщению (ссылка `compare_url`),
  не открывая `pilot-key.csv` и результаты замеров. Иначе оценка «ожидаю регрессию» теряет смысл.
- **`expect_regression = yes`** — только если аннотатор может назвать конкретный механизм ухудшения
  (новая зависимость в основном бандле, тяжёлый код при загрузке, новый баннер выше контента…).
  «Большой коммит» сам по себе не основание. `unsure` — механизм возможен, но не очевиден.
- **Улучшения не считаются регрессией**: удаление скрипта или ленивая загрузка → `no`, даже если
  изменение связано с производительностью (категорию при этом указать).
- **`expected_metrics`** заполняется только при `yes` или `unsure`; не больше трёх метрик.
- **`perf_category`** — одна, главная; при нескольких — та, что вероятнее всего влияет на метрику.
- **Фаза 2**: `is_cause = yes` — не больше трёх файлов на регрессию; удалённые целиком файлы и
  файлы, не попадающие в сборку (CI, исходники шрифтов `.sfd`, тесты), — `no`.
- **Комментарий** — до 150 символов, одной фразой: механизм, а не пересказ diff.
- **LCP-элемент**: `is_page_content = yes`, только если элемент — основное содержимое, ради которого
  открывают страницу (текст руководства, код диаграммы, слова теста); логотип, подсказки, промо — `no`.
- **Ключевые слова-подсказки** для категорий (не правило, а помощь): `dependency` — package.json,
  lock-файл; `event_handler` — `addEventListener`, `onClick`, `@input`; `timer_animation` —
  `setTimeout`, `setInterval`, `requestAnimationFrame`; `code_splitting` — `import(`, `lazy(`;
  `font` — `@font-face`, `.woff2`; `dom_layout` — `getBoundingClientRect`, `offsetHeight`, `innerHTML`.

## Шаг 4. Уровни аннотаций

| Модальность | Уровень 1 | Уровень 2 | Уровень 3 |
|---|---|---|---|
| Замеры | Пара «база → коммит» | Метрика | Прогон |
| Текст: изменение кода | Коммит | Файл (фрагмент) | Строка (шаблон кода) |
| Текст: страница | Страница | LCP-элемент | Атрибуты элемента |

- для **замеров**:
  - уровень 1: пара — итоговая метка `regression` / `improvement` / `none`;
  - уровень 2: метрика — метка по LCP, INP, TBT, CLS с разностью медиан и q-значением;
  - уровень 3: прогон — обычный, выброс или ошибка; какой элемент стал LCP;
- для **текста изменения кода**:
  - уровень 1: коммит — ожидается ли регрессия, по каким метрикам, тип и категория изменения;
  - уровень 2: файл — вызвал ли он регрессию и через какой механизм;
  - уровень 3: строка — какой шаблон кода в ней (обработчик, таймер, импорт, работа с DOM…);
- для **текста страницы**:
  - уровень 1: страница проекта, на которой мерили;
  - уровень 2: LCP-элемент — его категория и основной ли это контент;
  - уровень 3: атрибуты — селектор, видимый текст, тег.

Чем ниже уровень, тем больше автоматизации: уровень 3 везде размечается программно, уровень 1 замеров —
статистическим критерием, ручной труд нужен на уровнях 1–2 текста.

## Шаг 5. Формат аннотаций для каждой модальности

| Модальность | Способ аннотирования | Хранение |
|---|---|---|
| Замеры | метки на уровне пары и метрики; флаги на уровне прогона | таблица CSV, связанная с исходным JSON по `sha` |
| Текст: изменение кода | метки на коммит и на файл; «области выделения» — номера строк с шаблоном | CSV (уровни 1–2), JSONL с привязкой к файлу и строке (уровень 3) — внешняя (stand-off) разметка, исходный diff не изменяется |
| Текст: страница | метка категории на уникальный элемент | CSV, связанный с прогонами по `element_id` |

Внешняя разметка выбрана потому, что diff и замеры большие и уже лежат в наборе данных: аннотация
ссылается на них по `sha`, пути файла и номеру строки, а не копирует их.

## Шаг 6. Верификация аннотаций

### Автоматический слой

| Что проверяется | Как | Результат |
|---|---|---|
| Ложные метки регрессии | **A/A-сравнения**: одинаковый код измеряется как пара, любая метка — ложная | 68 сравнений, 1 ложная метка |
| Пропуск регрессий | **мутанты**: в коммит внедряется регрессия известной силы | кривые чувствительности (`results/sensitivity-*.json`) |
| Устойчивость к выбросам | критерий Манна – Уитни ранговый; прогоны-выбросы отмечаются на уровне 3 | 22–32 % прогонов имеют выброс хотя бы по одной из 6 метрик, 5–10 % — по отдельной |
| Категория LCP-элемента | правила сверены с ручной проверкой (аннотатор B), каппа Коэна | κ = 0,40; верны для 12 из 24 элементов и 82 % прогонов — ниже порога 0,6, ручной слой обязателен |

### Ручной слой

- **Обучение аннотаторов.** Инструкция — этот документ (шаги 2–3) и разобранные примеры ниже.
- **Пилотная выборка.** 50 пар: все 25 регрессий четырёх проектов и 25 пар без регрессии из тех же
  проектов в той же пропорции, порядок перемешан, метки скрыты. Пилот разметил один аннотатор —
  **B**, языковая модель Claude, по инструкции этого документа. Ограничение: B видел измеренные метки
  шести пар раньше (отмечены `label_seen_before = yes`) — для них сравнение считается отдельно.
- **Проверка по эталону.** У ручной разметки фазы 1 есть независимый эталон — измеренная метка
  регрессии (`pilot-key.csv`): `python ml/annotation.py agree` сравнивает с ним оценку аннотатора
  (полнота и точность). Это проведено для B (результаты ниже).
- **Перекрёстное аннотирование (процедура).** Для перехода от пилота к полной разметке второй
  аннотатор (A) независимо размечает ту же выборку по той же инструкции, не видя ни эталона, ни
  разметки B; листы — `*.template.csv`, файл — `pilot-phase1.A-<фамилия>.csv`. Согласие считается той же
  командой: `python ml/annotation.py agree A-<фамилия> B-claude`. Та же мера уже применена к паре
  «правила — ручная проверка» для LCP-элементов (таблица выше).
- **Мера согласия** — каппа Коэна по каждому полю (`python ml/annotation.py agree A-<фамилия> B-claude`):
  κ ≥ 0,6 — согласие приемлемое; 0,4–0,6 — уточнить инструкцию по расходящимся категориям; < 0,4 —
  пересмотреть словарь (возможно, слишком дробный).
- **Проверка ошибок.** Каждая 5-я пара выборки (P05, P10, …, P50) после разметки пересматривается
  обоими аннотаторами совместно; найденные ошибки — повод пересмотреть остальные пары той же категории.
- **Итеративность.** Расхождения обсуждаются, инструкция уточняется, спорные пары размечаются заново;
  версия инструкции фиксируется в истории репозитория.
- **Документирование.** Результат согласования — `annotations/agreement.json`; изменения инструкции —
  в этом документе.

Дополнительная проверка, которую даёт слепая фаза: насколько **человек по diff** угадывает
измеренную регрессию — это нижняя граница «экспертного» прогноза для сравнения с моделью.

### Разобранные примеры

| Пара | Оценка | Почему |
|---|---|---|
| monkeytype «chore: add tailwind» | `yes`, `lcp;cls`, `build`, `css` | новый CSS-фреймворк перестраивает стили всех страниц; LCP 1,9 → 3,0 с |
| excalidraw «Update translations from Crowdin» | `unsure`, `lcp`, `content`, `content` | обычно нейтрально, но excalidraw измерен в ru-RU, и текст приветствия был LCP-элементом |
| vuejs-docs «delete perfops script» | `no`, —, `build`, `third_party` | удалён скрипт — ожидается улучшение, не регрессия |
| mermaid «renovate/patch-mermaid-packages» | `unsure`, `tbt` | патч библиотеки диаграмм может изменить время отрисовки в сценарии |

### Первые результаты (аннотатор B)

- Фаза 1: из 50 пар B ожидает регрессию в 16 — среди них 14 настоящих (полнота 56 %, точность 88 %);
  только по слепым парам — 10 из 19 (53 %, 83 %).
- LCP-элемент — основное содержимое страницы только в **45 % прогонов**; в остальных — промо-плашки
  (mermaid, vuejs), объявление (monkeytype), подсказка в подвале или логотип. Это угроза валидности
  метрики LCP в лаборатории: изменения баннеров меняют LCP сильнее, чем изменения контента.
