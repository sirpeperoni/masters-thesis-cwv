# Концепции проекта

Что лежит в основе системы прогнозирования регрессий Core Web Vitals: предметная область,
инструменты измерения, дизайн эксперимента, статистика и план ML-части.
Для каждого решения указано, **зачем** оно принято и **где** реализовано: из этого текста
собираются главы «Методика» и «Угрозы валидности».

---

## 1. Предметная область

### 1.1. Core Web Vitals

Метрики Google для пользовательского опыта. Оценивается 75-й перцентиль реальных посещений.

| Метрика | Что измеряет | Хорошо | Плохо |
|---|---|---|---|
| **LCP** — Largest Contentful Paint | когда отрисован самый крупный элемент первого экрана (скорость загрузки) | ≤ 2,5 с | > 4 с |
| **INP** — Interaction to Next Paint | задержка от действия пользователя до следующей отрисовки, худшая за сессию (отзывчивость) | ≤ 200 мс | > 500 мс |
| **CLS** — Cumulative Layout Shift | суммарный неожиданный сдвиг вёрстки (визуальная стабильность) | ≤ 0,1 | > 0,25 |

INP заменил FID в марте 2024 года.

### 1.2. Лабораторные и полевые данные

- **Полевые данные** (RUM, CrUX) собираются у реальных пользователей. Они привязаны
  к версии сайта в продакшене, а не к коммиту, и очень шумные. Для JIT-предсказания не подходят.
- **Лабораторные данные** получаются в контролируемом браузере на конкретной сборке.
  Их можно привязать к коммиту. В работе используются только они.

**Вспомогательные лабораторные метрики:**
- **TBT** (Total Blocking Time) — сумма «лишнего» времени длинных задач главного потока
  (`длительность − 50 мс` для задач длиннее 50 мс). Стандартный лабораторный заменитель INP:
  при обычной загрузке взаимодействий нет, и INP просто не существует.
- **FCP** (First Contentful Paint) — вспомогательная метрика загрузки. Speed Index не используется.

### 1.3. JIT-предсказание (Just-In-Time)

Оценка риска изменения **в момент коммита**, до слияния и выкладки. Термин пришёл из
JIT-предсказания дефектов (Kamei и др.; JITLine, JIT-Fine). Метку «коммит внёс дефект»
там обычно получают алгоритмом **SZZ** — от коммита-исправления назад к внёсшему ошибку коммиту.

В этой работе метка получается **прямым измерением**: каждая пара «база → коммит» измеряется
в лаборатории. Отсюда нет и шума разметки SZZ, на который жаловались PerfJIT и работа Böck
о Firefox.

## 2. Измерение: инструменты

### 2.1. Lighthouse и режимы user flow

Код: [bench/src/measure.ts](../bench/src/measure.ts). Lighthouse 13 умеет три режима:
- **navigation** — загрузка страницы с нуля: LCP, CLS, TBT, FCP (Speed Index не считается — не используется);
- **timespan** — произвольный отрезок времени, в который скрипт выполняет действия
  пользователя: INP, TBT, CLS за этот отрезок;
- **snapshot** — состояние страницы в один момент (не используется).

**User flow** склеивает режимы в одну сессию браузера. Каждый прогон — это navigation,
затем timespan со сценарием из конфига репозитория. Для excalidraw сценарий такой:
фигуры, стрелка, ввод текста, выделение всего, перетаскивание, отмена
([bench/repos/excalidraw.ts](../bench/repos/excalidraw.ts)).

### 2.2. Замедление: simulate и devtools

- **simulate (Lantern)** — страница грузится без замедления. Затем Lighthouse строит граф
  зависимостей запросов и задач и **моделирует** загрузку в заданных условиях.
  Плюсы: низкий шум. Минусы: это модель.
  Lighthouse параллельно отдаёт **наблюдаемые** значения (`observed*`), и стенд сохраняет оба варианта.
- **devtools** — замедление реально применяется через Chrome DevTools Protocol.
  Реалистичнее, но шумнее. Timespan поддерживает только этот вариант, поэтому INP измеряется так.

Настройки одинаковы для всех проектов:
- экран десктопный, 1350×940;
- **CPU замедлен в 4 раза**: без этого на быстрой машине TBT и INP почти всегда около нуля и сигнала нет;
- RTT 40 мс, канал 10 Мбит/с.

Настройки сохраняются в каждый результат (`env.settings`).

### 2.3. Изоляция и чистое состояние

- **Отдельный рабочий процесс Node на каждый коммит**
  ([measure-worker.ts](../bench/src/measure-worker.ts), [worker-client.ts](../bench/src/worker-client.ts)).
  Lighthouse в долгоживущем процессе теряет около 0,5 ГБ памяти на коммит и падает от её нехватки.
  Процесс перезапускается **на границе коммитов**, поэтому перезапуск никогда не попадает
  внутрь серии A/B и не влияет на одну версию сильнее, чем на другую. Раньше новый процесс
  запускался на каждый прогон, и это стоило 3–4 с (старт Node, tsx, импорт Lighthouse).
- **Новый временный профиль Chrome на каждый прогон**: холодный кеш, без cookies и service worker.
- **Лёгкий прогрев** обеих версий перед замерами: одна загрузка страницы в Chrome без Lighthouse.
  Убирает эффекты первого запуска: дисковый кеш ОС, JIT-компиляцию сервера и нового рабочего
  процесса. Полный прогон Lighthouse для этого не нужен.
- **Только нужные аудиты** (`onlyAudits`) вместо всей категории performance (~49 аудитов),
  без полностраничного скриншота. Speed Index не считается. Прогон стал примерно на 10% быстрее.
  Замер на одной сборке: 16,2 с против 14,5 с.
- **Собственный статический сервер** ([server.ts](../bench/src/server.ts)) со сжатием gzip,
  как у CDN, и SPA-fallback. Сервер один для всех проектов, чтобы сетевой слой не влиял на сравнение.

## 3. История репозитория и сборки

Код: [bench/src/git.ts](../bench/src/git.ts), [run.ts](../bench/src/run.ts), [bundle.ts](../bench/src/bundle.ts).

- **First-parent история** (`git log --first-parent`) — последовательность состояний главной
  ветки, каждое слияние PR считается одним шагом. Промежуточные коммиты внутри веток не берутся:
  они никогда не были в продакшене.
- **Фильтр по путям** (git pathspec) отбрасывает коммиты, которые не трогают приложение:
  документацию, CI, тесты.
- **Частичный клон** (`--filter=blob:none`) — полная история без скачивания всех версий файлов.
- **Кеш зависимостей по хешу lock-файла.** `yarn install` выполняется, только если
  изменился `yarn.lock`. Это главная экономия времени.
- **Устаревание истории.** Старые коммиты требуют старый Node (18–20). Проверку версии
  отключает `YARN_IGNORE_ENGINES`. Коммиты, которые не собираются, получают статус
  `build_failed` или `install_failed`. Их долю нужно показать в угрозах валидности.
- **Хеш содержимого сборки** (SHA-256 от отсортированных путей и байтов файлов, без source maps).
  Сборки Vite **воспроизводимы**: повторная сборка того же коммита даёт тот же хеш, это проверено.
  Одинаковый хеш у базы и коммита означает, что пользователь получает побайтно то же приложение.
- **Кеш сборок.** Сборка коммита сохраняется и сразу служит базой для следующего,
  так что каждый коммит собирается один раз.

## 4. Дизайн эксперимента

### 4.1. Единица наблюдения — пара «база → коммит»

Целевая переменная — не абсолютное значение метрики, а **изменение относительно базы**.
База — последняя успешно собранная версия перед коммитом; у первого коммита диапазона —
его git-родитель. Абсолютные значения зависят от машины, а изменение внутри одной сессии
замеров гораздо устойчивее.

### 4.2. Дрейф и чередование (контрбалансировка ABBA)

**Проблема**, найденная на пилотных данных: при последовательной схеме (сначала все прогоны
коммита 1, потом коммита 2) состояние машины меняется во времени. Фоновые процессы,
температура и частота CPU дают «значимые» разницы между коммитами с одинаковым кодом.
В пилоте коммит с нулевым изменением JS дал TBT +61 мс при p = 0,01, а следующий коммит — −60 мс.

**Решение**: база (A) и коммит (B) измеряются вперемешку в порядке **AB BA AB BA…**
- Медленный дрейф одинаково влияет на обе версии и вычитается при сравнении.
- Смена порядка внутри пары (контрбалансировка) гасит эффект позиции: например,
  «второй прогон подряд всегда быстрее». При линейном дрейфе блок ABBA несмещён.
- У каждого прогона есть номер `seq`, по нему дрейф можно проверить явно.

### 4.3. Контрольные A/A-сравнения

Если сборки базы и коммита совпали, различий нет **по построению**. Каждое 5-е такое
сравнение всё равно измеряется. Доля A/A-сравнений, которые разметка ошибочно назвала
изменением, — это **эмпирическая доля ложных срабатываний** всей процедуры: и с измерениями,
и со статистикой. Так проверяется реальный уровень ошибки, а не номинальные α = 0,05.

Одинаковые сборки соседних коммитов оказались редкими: около 2%. Фильтр по путям уже
отсекает почти все коммиты, не трогающие приложение. Поэтому A/A-пары добираются второй
процедурой: каждый 15-й измеренный коммит дополнительно сравнивается **сам с собой** —
одна и та же сборка на двух серверах, та же схема ABBA, то же правило расширения
(`<sha>.aa.json`, флаг `selfAA`). На весь репозиторий это около 30 контрольных пар.

### 4.4. Адаптивное число прогонов (двухэтапная выборка)

- **Этап 1:** 5 пар для каждого коммита.
- **Этап 2:** если хоть одна метрика «подозрительна» (p < 0,1 **и** |Δ| ≥ половины порога),
  добавляется ещё 10 пар.

Ресурсы тратятся там, где решение неочевидно.

**Как правило менялось по данным.** Сначала было «p < 0,1 **или** |Δ| ≥ порога». На первых
~160 коммитах серия расширялась у 31% из них. Это почти столько же, сколько дал бы чистый шум:
у каждой из 5 метрик p < 0,1 случайно выпадает примерно в 10% случаев, и вместе это даёт около
30–40%. Среди расширенных оказалась и одна A/A-пара с одинаковым кодом. Из 53 расширенных
коммитов итоговую метку изменения получили только 3. После этого условие ужесточили до «и»
с половиной порога.

Правило записывается в каждый результат (`method.extendRule`). В ранних файлах поля нет,
там действовало старое правило. На корректность меток смена правила не влияет: метки ставятся
по всем прогонам с поправкой BH. Меняется только число прогонов, а значит, мощность
для отдельных коммитов.

**Оговорка для раздела об ограничениях.** Решение продолжать по промежуточным данным
(optional stopping) формально немного завышает ошибку I рода. В работе это компенсируется
тремя вещами:
1. практическим порогом;
2. поправкой BH;
3. прямой оценкой ложных срабатываний на A/A.

Более строгая альтернатива — групповой последовательный дизайн с поправкой α по этапам
(Pocock, O'Brien–Fleming).

### 4.5. Искусственные регрессии (мутанты)

Реальных регрессий мало (~1,4% в excalidraw), а по INP и CLS их нет совсем. Поэтому в реальные
коммиты внедряются известные антипаттерны **заданной силы** ([mutations.ts](../bench/src/mutations.ts)):
- блокирующий скрипт в `<head>` (LCP), 25–200 мс;
- долгая задача при старте (TBT), 50–400 мс;
- тяжёлый обработчик ввода (INP), 10–100 мс;
- сдвиг вёрстки (CLS), 10–300 px;
- «раздутый» бандл, 50–800 КБ.

Мутант — это **реальный коммит плюс вставка**, а база та же, что в основном датасете.
Поэтому у мутанта настоящий diff, и он не выглядит искусственным однострочным изменением.
Собственный эффект коммита известен из основного датасета и почти всегда около нуля.

Два назначения:
1. **Кривая чувствительности стенда**: доля обнаруженных регрессий в зависимости от силы
   антипаттерна. Это эмпирический MDE для RQ1, надёжнее формулы из п. 5.4.
2. **Размеченные положительные примеры** по всем метрикам для обучения и проверки моделей.

Ограничение для раздела угроз: мутанты проще реальных регрессий (один явный паттерн), поэтому
модель, обученная на них, может выучить сам паттерн. Их стоит использовать для проверки
чувствительности и как дополнение к обучающим данным, но оценивать модель — на реальных регрессиях.

### 4.6. Пропуск одинаковых сборок

Если сборка побайтно совпала с базой, коммит получает статус `identical_build`
(метка «без изменений») и не измеряется. Это экономит около 5 минут на каждом таком коммите:
в пилоте таких было 2 из 2. Заодно появляется источник A/A-сравнений.

## 5. Статистика

Код: [bench/src/stats.ts](../bench/src/stats.ts).

### 5.1. Робастные оценки

Распределения прогонов имеют **тяжёлые хвосты**: редкие медленные прогоны из-за фоновой активности.
Поэтому:
- центр — **медиана**, а не среднее;
- разброс — **IQR**, межквартильный размах $Q_3 - Q_1$, и **CV**, коэффициент вариации
  $\sigma/\mu$, для сравнения метрик разного масштаба;
- изменение считается как разность медиан: $\Delta = \operatorname{med}(B) - \operatorname{med}(A)$.

### 5.2. Тест Манна–Уитни (сумм рангов Уилкоксона)

Непараметрический тест: нормальность не нужна, выбросы влияют слабо. Нулевая гипотеза:
значения базы и коммита одинаково распределены.

$$U = R_1 - \frac{n_1(n_1+1)}{2},$$

где $R_1$ — сумма рангов выборки A в объединённом ряду.

- **Точное распределение** (выборки ≤ 20, без совпадающих значений).
  Число перестановок с данным $U$ считается рекуррентно:
  $f(m,k,u) = f(m-1,k,u-k) + f(m,k-1,u)$.
  Двустороннее $p = 2\,\min\{P(U \le u),\, P(U \ge u)\}$.
  Для 5 пар минимально возможное $p = 2/252 \approx 0{,}008$.
- **Нормальное приближение** (есть совпадения или большие выборки):
  $$\mu_U = \frac{n_1 n_2}{2},\qquad \sigma_U^2 = \frac{n_1 n_2}{12}\left((n+1) - \frac{\sum (t^3 - t)}{n(n-1)}\right),$$
  где $t$ — размеры групп совпадающих значений. К $|U - \mu_U|$ добавляется поправка
  на непрерывность 0,5.

Реализация сверена с эталонными значениями: $p = 0{,}00794$ для [1..5] против [6..10].

### 5.3. Множественные сравнения: FDR и Бенджамини–Хохберг

На сотни коммитов и 5 метрик приходятся тысячи проверок. При α = 0,05 каждая 20-я
проверка без изменения даст ложную «значимость».

- **FWER** (поправка Бонферрони) контролирует вероятность хотя бы одной ложной находки.
  Это слишком строго: реальные регрессии будут пропущены.
- **FDR** (False Discovery Rate) контролирует **ожидаемую долю** ложных среди найденных.
  Для разметки датасета это правильная цель.

Процедура Бенджамини–Хохберга: упорядочить $p_{(1)} \le \dots \le p_{(m)}$ и вычислить q-value

$$q_{(i)} = \min_{j \ge i} \frac{m\, p_{(j)}}{j}.$$

Изменение считается значимым при $q < 0{,}05$. Поправка применяется **отдельно по каждой
метрике** по всем сравнениям репозитория, включая A/A. Поэтому разметка выполняется отдельным
шагом ([label.ts](../bench/src/label.ts)) после сбора, а не во время него.

### 5.4. Практическая значимость и MDE

Статистическая значимость говорит «разница есть», но не «разница важна».
Метка ставится, только если $|\Delta| \ge \max(\text{abs},\ \text{rel}\cdot\text{база})$:

| Метрика | abs | rel | Обоснование |
|---|---|---|---|
| LCP | 50 мс | 5% | MDE LCP около 5–6% в обоих репозиториях; 50 мс — заметный вклад в бюджет 2,5 с |
| INP | 20 мс | 10% | 10% от «хорошего» порога 200 мс; у тяжёлых приложений — 10% от их собственного INP |
| TBT | 30 мс | 10% | у лёгкого приложения работает абсолютная часть, у тяжёлого — относительная |
| CLS | 0,01 | — | 10% от «хорошего» порога 0,1; CLS детерминирован |

**Почему максимум, а не одно абсолютное число.** Шум зависит от приложения. A/A на 10 парах:

| | excalidraw (MDE при 15 парах) | mermaid-live-editor (MDE при 15 парах) |
|---|---|---|
| LCP | 59 мс (6%) | 184 мс (5%) |
| INP | 11 мс (9%) | 52 мс (19%) |
| TBT при загрузке | 15 мс | 376 мс (50%) |
| TBT в сценарии | — | 553 мс (18%) |

У mermaid (редактор Monaco + mermaid, TBT при загрузке ~0,75 с) абсолютные 20–30 мс
превышаются одним шумом. В относительных величинах **LCP ведёт себя одинаково** (~5–6%),
а INP и TBT у тяжёлого приложения шумнее. Первоначально было: LCP — min(50 мс, 5%),
остальные — только абсолютный порог. Переход на max **не изменил ни одной метки excalidraw**
(225 коммитов): у лёгкого приложения относительная часть не срабатывает.

**MDE** (minimum detectable effect) — наименьший эффект, который обнаруживается
с мощностью 80% при α = 0,05:

$$\text{MDE} \approx (z_{0{,}975} + z_{0{,}8})\,\sigma\sqrt{2/n} \approx 2{,}8\,\sigma\sqrt{2/n}.$$

Порог и MDE — разные вещи. Порог отвечает на вопрос «какое изменение **важно**», MDE — «какое
изменение стенд **надёжно видит**». Если порог меньше MDE, регрессии между ними обнаруживаются
с мощностью ниже 80%. У mermaid так с TBT: порог 10% против MDE 50%. Это нормально — метки
ставит статистический тест, ложных срабатываний не прибавится (проверяется на A/A), но часть
реальных регрессий средней величины останется «без изменений». Это нужно указать в угрозах
валидности, а чувствительность каждого репозитория показать отдельно — эмпирически, по мутантам.

### 5.5. Итоговое правило разметки

Для каждой метрики:
- **регрессия** — если $q < 0{,}05$ и $\Delta \ge \text{порог}$;
- **улучшение** — если $q < 0{,}05$ и $\Delta \le -\text{порог}$;
- **без изменений** — иначе, а также при `identical_build`.

Коммит в целом — регрессия, если есть регрессия хотя бы по одной метрике.

### 5.7. Шум на основной схеме (A/B, чередование) — `npm run rq1`

Внутри пары прогоны базы между собой — один и тот же код, прогоны коммита — тоже. Поэтому
шум оценивается **по каждой измеренной паре**, а не только по A/A: сотни оценок вместо
десятка. Excalidraw, 229 пар (29.09.2026), медианы по сторонам:

| Метрика | Медиана | CV (медиана / p90) | MDE, n = 5 | MDE, n = 15 | Порог при медиане |
|---|---|---|---|---|---|
| LCP | 1129 мс | 4,4% / 8,8% | 92 мс (8%) | 53 мс (5%) | 56 мс |
| INP | 108 мс | 9,1% / 13,7% | 18 мс | 11 мс | 20 мс |
| TBT при загрузке | 72 мс | 18% / 34% | 22 мс | 13 мс | 30 мс |
| TBT в сценарии | 17 мс | 35% / 72% | 12 мс | 7 мс | 30 мс |
| CLS | 0,0004 | 0% / 8% | 0 | 0 | 0,01 |

При 15 парах **все пороги не меньше MDE**. Опасение из п. 5.4 про порог LCP снято:
MDE 53 мс при пороге 56 мс.

A/A в датасете: 7 сравнений, 35 проверок. p < 0,05 без поправки — у 1 (2,9% при ожидаемых 5%),
ложных меток после всей процедуры — 0. Признаков дрейфа нет: чередование ABBA работает.

Для mermaid-live-editor данные есть пока только из A/A пробы, они приведены в п. 5.4.
Этот репозиторий существенно шумнее.

### 5.8. Чувствительность стенда по искусственным регрессиям — `npm run sensitivity`

Excalidraw, 6 коммитов × 19 мутантов (01.10.2026), обнаружение по **целевой** метрике
после всей процедуры (BH + порог):

| Оператор | Метрика | 1-й уровень | 2-й | 3-й | 4-й |
|---|---|---|---|---|---|
| long_task (задача при старте) | TBT | 50 мс — **100%** | 100 мс — 100% | 200 мс — 100% | 400 мс — 100% |
| slow_input (обработчик ввода) | INP | 10 мс — 0% | 25 мс — **50%** | 50 мс — 100% | 100 мс — 100% |
| layout_shift (сдвиг) | CLS | 10 px — 0% | 40 px — **100%** | 120 px — 100% | 300 px — 100% |
| blocking_script (`<head>`) | LCP | 25 мс — 0% | 50 мс — 0% | 100 мс — 17% | 200 мс — **67%** |
| bundle_bloat (байты) | LCP | 50 КБ — 17% | 200 КБ — 0% (4 из 6) | 800 КБ — 50% (2 из 6) | — |

- **Количественная проверка стенда:** Δ TBT ≈ 4 × длительность задачи − 50 мс
  (замедление CPU ×4 и порог блокирующей задачи 50 мс): 400 мс → +1551 мс при ожидаемых 1550.
- Нижняя граница обнаружения задаётся **практическим порогом**: 10 мс в обработчике дают
  ΔINP ≈ 4 мс < 20 мс, 10 px — ΔCLS 0,007 < 0,01. Это осознанный выбор, а не слепота стенда.
- `bundle_bloat` 200/800 КБ в новых версиях **не собирается**: PWA-плагин excalidraw отказывает
  при файле > 2 МиБ. Это бюджет размера, встроенный в сборку проекта: такой коммит в продакшен
  не попал бы. Часть регрессий отсекают существующие защиты, система нужна для остальных.

**Моделированный и наблюдаемый LCP видят разные регрессии** (медианы Δ по коммитам):

| Мутант | ΔLCP Lantern (simulate) | ΔLCP наблюдаемый |
|---|---|---|
| long_task 400 мс | +138 | **+402** |
| blocking_script 200 мс | +90 | +143 |
| bundle_bloat 800 КБ | **+283** | +58 |

Lantern моделирует сеть (10 Мбит/с) и хорошо видит лишние байты, но **недооценивает
блокировку главного потока**. Наблюдаемый LCP (без моделирования, сеть localhost) видит
задержки CPU почти 1:1, но не видит сетевых и шумнее (п. 5.6). Разметка построена на Lantern;
процессорные регрессии при этом не теряются — их ловит TBT (100% с 50 мс). Выбор метода
измерения определяет, **какой класс регрессий** виден по LCP: это нужно явно обсудить в RQ1.

**Поэтому добавлена вторая метка — `lcpObs` (наблюдаемый LCP)**, тот же порог max(50 мс, 5%).
Она **дополнительная**: не входит в итоговую метку коммита и в правило расширения серии
(`PRIMARY_TARGETS` в stats.ts), поэтому основная разметка и процедура сбора не изменились.
Результат (01.10.2026):

- мутанты long_task — обнаружено моделированным / наблюдаемым LCP: 50 мс 1/3, 100 мс 3/6,
  200–400 мс 4/6 (из 6); bundle_bloat — наблюдаемый не видит (сеть localhost);
- реальные коммиты excalidraw: смены LCP-элемента видят обе (наблюдаемый — с меньшими Δ),
  обновление firebase (сетевая регрессия) — только Lantern;
- mermaid: метки почти не пересекаются — Lantern ловит обновления зависимостей (байты),
  наблюдаемый — другие коммиты (редизайн −190 мс, `0683cdba` +71 мс);
- на A/A у `lcpObs` 0 ложных срабатываний (36 пар).

Значит, вторая метка даёт **новые** положительные примеры, а не дублирует первую.

**mermaid-live-editor, 6 коммитов × 19 мутантов (04.10.2026).** Шумный проект (п. 5.7) с отрисовкой
на клиенте (SvelteKit, страница `/edit`). Обнаружение по целевой метрике и по «соседней»:

| Оператор | Метрика | 1-й уровень | 2-й | 3-й | 4-й |
|---|---|---|---|---|---|
| long_task | TBT | 50 мс — 17% | 100 мс — 0% | 200 мс — 17% | 400 мс — 50% |
| long_task | **lcpObs** | 50 мс — 0% | 100 мс — 0% | 200 мс — 67% | 400 мс — **100%** |
| slow_input | INP | 10 мс — 17% | 25 мс — **83%** | 50 мс — 83% | 100 мс — 83% |
| slow_input | **TBT flow** | 10 мс — 83% | 25 мс — **100%** | 50 мс — 100% | 100 мс — 100% |
| layout_shift | CLS | 10 px — 0% | 40 px — **100%** | 120 px — 100% | 300 px — 100% |
| blocking_script | LCP | 25 мс — 0% | 50 мс — 33% | 100 мс — 17% | 200 мс — **67%** |
| bundle_bloat | LCP | 50 КБ — 0% | 200 КБ — 0% | 800 КБ — 0% | — |

- **TBT при загрузке не видит задачу, выполненную до первой отрисовки.** TBT по определению
  суммирует блокировку между FCP и моментом интерактивности. В excalidraw первая отрисовка ранняя,
  задача при старте целиком попадает в окно: 400 мс → Δ TBT +1550. В mermaid содержимое рисует JS,
  моделируемый FCP поздний (2,7–3,3 с), и задача частично или полностью оказывается **до** FCP:
  наблюдаемый FCP сдвигается на +300 мс, а Δ TBT колеблется от +470 до **−330** мс. Отрицательное
  значение получается, когда сдвинутый FCP выталкивает из окна уже существовавшие задачи. Наблюдаемый LCP
  ту же задачу видит стабильно: +300 мс у всех шести коммитов. Это довод в пользу второй метки
  `lcpObs` и ограничение TBT как лабораторной замены INP для приложений с отрисовкой на клиенте.
- **slow_input:** INP пропустил все уровни только на самом новом коммите (`1ab7e2e0`, 09.2026).
  Там у базы INP разбросан на 270–740 мс, и добавка 100 мс тонет в шуме. TBT сценария ловит
  тяжёлый обработчик на всех коммитах, начиная с 25 мс.
- **Чувствительность зависит от проекта.** Сдвиг вёрстки и блокирующий скрипт в `<head>` ловятся
  одинаково на обоих проектах. Процессорные регрессии надёжнее видны по метрике, которая для этого
  приложения устойчивее: для excalidraw по TBT, для mermaid по наблюдаемому LCP и TBT сценария.
  Поэтому разметку ведём по нескольким метрикам, а не по одной.
- bundle_bloat 800 КБ: Δ LCP Lantern +21 мс (у excalidraw +283). Бандл mermaid и так 5,8 МБ gzip,
  загрузка идёт кусками, и добавка в точку входа почти не меняет критический путь.

**monkeytype, 6 коммитов × 19 мутантов (06.10.2026).** У одного коммита не собрались 12 модульных мутантов
(102 из 114 измерены).

| Оператор | Метрика | 1-й уровень | 2-й | 3-й | 4-й |
|---|---|---|---|---|---|
| long_task | TBT | 50 мс — **100%** | 100 мс — 100% | 200 мс — 100% | 400 мс — 100% |
| slow_input | INP | 10 мс — 0% | 25 мс — 20% | 50 мс — **80%** | 100 мс — 100% |

| blocking_script | **lcpObs** | — | — | 100 мс — 17% | 200 мс — **83%** |

- **TBT при загрузке здесь работает, как в excalidraw**: Δ TBT ≈ 4 × длительность − 50 (400 мс → +1526),

## 6. ML-часть

Признаки уже реализованы ([ml/features.py](../ml/features.py), 116 штук). Diff берётся строго
между теми же базой и коммитом, что сравнивал стенд: если база была несколько коммитов назад,
в diff попадают все промежуточные изменения. Группы признаков:

| Префикс | Что | Примеры |
|---|---|---|
| `k_` | классические JIT-метрики (Kamei) | файлов, добавлено/удалено строк, директорий, подсистем, энтропия, опыт автора, возраст файлов, разработчиков файлов |
| `cat_` | что затронуто | файлы и строки кода, стилей, HTML, тестов, документации, конфигов; число картинок и шрифтов; «только тесты или документация» |
| `dep_` | зависимости в `package.json` | добавлено, удалено, обновлено, **мажорные** обновления — отдельно для `dependencies` и `devDependencies` |
| `pat_` | frontend-паттерны в добавленных и удалённых строках | импорты (статические и динамические), lazy/Suspense, эффекты, мемоизация, состояние, обработчики, таймеры, rAF, циклы, чтение layout, работа с DOM, canvas, воркеры, шрифты, картинки, их размеры, preload/lazy-загрузка, CSS layout и анимации |
| `msg_` | сообщение коммита | тип по Conventional Commits, revert, бот (Renovate, Dependabot), слова о производительности |
| `bnd_` | изменение сборки | Δ gzip всего, JS, CSS, числа файлов; относительные Δ |

`bnd_` требует сборки, но не замеров. Это «дешёвый» уровень признаков для системы в CI:
сборка там всё равно есть. Текст diff сохраняется в `.diffs.jsonl` для bag-of-words и CodeBERT.

**Первое наблюдение** (excalidraw, 218 пар). Обновление firebase 8 → 11 **уменьшило** JS
на 20 КБ, но дало регрессию LCP +102 мс. Обновление до React 19 **увеличило** JS на 24 КБ
без изменения метрик. Эвристика «вырос бандл — будет регрессия» ошибается в обе стороны.
Ранговые корреляции отдельных признаков с Δ слабые (|ρ| ≤ 0,22): у ~98% пар Δ — это шум
измерений, а сигнал сосредоточен в нескольких коммитах.

### План моделей

- **Задача.** Для каждой метрики — классификация по трём классам (регрессия / без изменений /
  улучшение) или бинарная «регрессия / нет». Дополнительно — регрессия величины Δ.
- **Признаки из diff:**
  - классические JIT-метрики изменения (по Kamei): строки, файлы, энтропия изменения, опыт автора;
  - frontend-специфичные: `package.json` и lock-файл, новые `import`, CSS и layout,
    изображения и шрифты, React-хуки, lazy/Suspense;
  - **Δ размера бандла** — его можно посчитать одной сборкой, без Lighthouse;
  - текстовые представления diff: bag-of-words как в JITLine и работе Böck, эмбеддинги CodeBERT/UniXcoder.
- **Модели** по возрастанию сложности:
  1. эвристика «вырос бандл»;
  2. логистическая регрессия;
  3. LightGBM;
  4. дообученный CodeBERT;
  5. LLM без дообучения (zero-shot).
- **Дисбаланс классов.** Регрессий меньше нескольких процентов. Отсюда взвешивание классов
  и оценка по PR-AUC и MCC, а не по accuracy и ROC-AUC. Дополнительно — искусственные
  регрессии, внедрённые в реальные коммиты.
- **Оценка:**
  - разбиение **строго по времени**: обучение на прошлом, проверка на будущем, без утечки;
  - перенос между проектами (cross-project);
  - метрики с учётом затрат на проверку: Recall@20% кода, Popt.

## 8. Угрозы валидности (заготовка)

- **Внутренняя валидность:**
  - остаточный дрейф (контролируется ABBA и A/A);
  - optional stopping (п. 4.4);
  - модель Lantern вместо реального замедления для LCP.
- **Конструктная валидность:**
  - лабораторные метрики ≠ полевые, TBT — лишь заменитель INP;
  - INP зависит от выбранного сценария взаимодействий.
- **Внешняя валидность:**
  - мало репозиториев;
  - приложения-холсты (excalidraw) почти не меняют CLS;
  - одна машина и одна версия Chrome.
- **Выживаемость:** несобираемые коммиты (`build_failed`) выпадают из датасета.
- **LCP-элемент — не всегда «содержимое страницы».** С 29.09.2026 стенд сохраняет, какой
  элемент был LCP, и фазы LCP (`lcpElement`, `lcp_*`). Оказалось:
  - у excalidraw LCP-элемент — **текст приветственного экрана**. Поэтому коммиты, меняющие
    только этот текст (обновления переводов Crowdin, «Clarify welcome screen message…»),
    получили метки LCP ±240 мс. Метрика изменилась честно, производительность — нет;
  - у mermaid-live-editor LCP-элемент — **рекламный баннер** («Try Mermaid Advanced Editor…»).
    LCP зависит от маркетинговых текстов.

  Это ограничение самого определения LCP. Для модели такие метки — законные положительные
  примеры («коммит изменил LCP»), но в разборе ошибок и в угрозах валидности их нужно выделять.
- **Язык браузера.** До 29.09.2026 он не фиксировался, и Chrome брал язык системы:
  **excalidraw измерен в ru-RU** (весь датасет — одинаково, пары сопоставимы). Дальше язык
  фиксирован явно — `--lang=en-US` (`env.lang` в результатах), иначе эксперимент
  не воспроизводится на машине с другим языком.
- **Внешние запросы.** Excalidraw при загрузке обращается к своему CDN (шрифты, ресурсы)
  и к аналитике. Время их ответа зависит от интернета. Датасет excalidraw собран без блокировки:
  внешний шум действует на обе стороны пары одинаково, но увеличивает дисперсию. Блокировать CDN
  нельзя: без шрифтов LCP вырос с ~1,2 до 3,4 с, приложение становится другим. Для новых
  репозиториев блокируется только аналитика и реклама (`blockedUrlPatterns`), а внешние домены
  каждой пары записываются в результат (`externalHosts`).
