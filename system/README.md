# cwv-risk — оценка риска регрессии Core Web Vitals

Ядро и консольная утилита «системы» диссертации (задачи е–ж введения): по изменению кода — коммиту или ветке
pull request — оценивает, насколько вероятно, что оно ухудшит LCP, INP, CLS или TBT, и советует, нужно ли
измерять его на стенде. Сборка и замеры для оценки не нужны.

## Как работает

1. **Признаки изменения** `merge-base(base, head) → head` — тот же код, что в экспериментах (`ml/features.py`):
   размер и разброс, что затронуто (код, стили, изображения, шрифты, конфиги), зависимости package.json,
   фронтенд-паттерны в добавленных и удалённых строках, сообщение коммита.
2. **Шкала проекта.** Признаки переводятся в перцентили относительно последних N коммитов основной ветки
   (по умолчанию 300; признаки истории кешируются в `<репозиторий>/.cwv-risk/history.csv`): модель оценивает,
   насколько изменение необычно для *этого* проекта, — так она переносится на проекты, которых не видела.
3. **Модель** — случайный лес на перцентилях (`models/forest-v1.joblib`), обучен на 4 полностью размеченных
   проектах (1329 изменений, 39 регрессий). Это модель, проверенная на 11 новых проектах (docs/results.md).
4. **Уровень риска** — по месту изменения среди истории проекта, с долей регрессий, наблюдавшейся на этом
   уровне в проверке на 11 проектах:

   | Уровень | Место среди истории | Регрессий в проверке | Рекомендация |
   |---|---|---|---|
   | высокий | верхние 5 % | 8,6 % (25 из 291) | измерить на стенде до слияния |
   | повышенный | 5–20 % | 2,8 % (24 из 869) | измерить, если есть время на замеры |
   | низкий | ниже 20 % | 0,7 % (2 из 279) | замеры можно пропустить |

5. **Объяснение** — признаки, по которым изменение необычно велико для проекта (перцентиль ≥ 80 %), по убыванию
   «важность в модели × необычность».

## Использование

Из папки `system/` (Python — `E:\Anaconda\python.exe`; зависимости — pandas, numpy, scikit-learn, joblib, typer):

```
python -m cwv_risk train                                       # обучить модель → models/forest-v1.joblib
python -m cwv_risk score --repo <путь> --base origin/main --head HEAD
python -m cwv_risk score --repo <путь> --base origin/main --head HEAD --format markdown   # для комментария в PR
python -m cwv_risk score ... --format json                     # для веб-панели и других программ
python -m cwv_risk score ... --fail-on high                    # код возврата 1 при высоком риске (проверка в CI)
```

Опции: `--history N` — длина шкалы; `--path src --path package.json` — учитывать в истории только фронтенд.
Первый запуск на проекте считает признаки истории (~2 мин на 200 коммитов), повторные — секунды.

## Проверка

- Коммит bentopdf f30a084f (27.12.2025; включил загрузку 71 МБ WebAssembly на главной, TBT +21 с) —
  **высокий риск, верхние 3 %** истории проекта.
- Прогон по 102 измеренным коммитам bentopdf (шкала — история до каждого коммита): высокий — 22 коммита,
  4 регрессии; повышенный — 53, 4; низкий — 27, 0. Все 8 регрессий — в высоком или повышенном уровне.
  (Измерены в основном коммиты, отобранные моделью, поэтому это проверка согласованности утилиты с моделью
  эксперимента, а не новая оценка качества.)

## GitHub Action

`action.yml` (в публичном репозитории — в корне: `uses: sirpeperoni/masters-thesis-cwv@main`): оценка, комментарий
в PR (один, обновляется), сводка проверки, кеш признаков истории, `fail-on`. Демо — форк bentopdf,
https://github.com/sirpeperoni/bentopdf/pulls (`scripts/demo-fork.ps1`): PR с WASM 71 МБ — высокий риск, однострочное
исправление — низкий.

## Очередь замеров (связка со стендом)

```
PR ──► Action: оценка риска ──► высокий? ──► метка «cwv-risk: measure»
                                                   │  (агент опрашивает GitHub; входящих подключений нет)
машина со стендом: python -m cwv_risk queue ◄──────┘
   └─► забрать коммиты PR и базы → стенд: npm run bench -- --repo <проект> --pair <база>:<PR>
       → data/<проект>-pr/ → разметка → раздел «Замер на стенде» в комментарии
       → метки «cwv-risk: measured» + «cwv-risk: regression» | «cwv-risk: ok»
```

```
python -m cwv_risk queue --github sirpeperoni/bentopdf --bench bentopdf [--once] [--interval 600]
```

- Действие ставит метку при уровнях `measure-on` (по умолчанию `high`); новые коммиты в PR снимают метки прежнего
  замера. Нужны права workflow `pull-requests: write` и `issues: write`.
- Стенд не запускается в облаке GitHub (нужны Chrome и простаивающая машина) и не запускается по событию из
  интернета: агент сам забирает задания — чужой код из PR не исполняется без участия владельца машины.
- Замеры PR — отдельный датасет `data/<проект>-pr/`: история измеренных изменений проекта, на ней со временем
  обучается текстовая модель проекта (docs/results.md: внутри истории лес + текст лучше одного леса).

## Веб-панель

FastAPI + SQLite (бэкенд, `cwv_risk/web/`) и React + Vite + TypeScript (фронтенд, `web/`; графики — Recharts).

Всё — нажатиями, без ввода хешей: проекты — в меню слева, изменения — строками таблиц и точками графиков,
проверка — выбором из списков.

| Экран | Что показывает |
|---|---|
| Сводка | ключевые цифры, кривая «доля проверенных коммитов → доля найденных регрессий» (модель, «большой коммит», случайный выбор), уровни риска |
| **+ Добавить проект** | любой открытый репозиторий GitHub: ссылка или пример одним нажатием, длина истории (100/200/500 коммитов). Фоновое задание: клон без файлов → признаки → прогноз; прогресс по шагам. Код — `cwv_risk/web/external.py`, клоны — `work/external/` |
| Проект → Коммиты | коммиты во времени (высота — риск; цвет — итог замера или, у сторонних проектов, уровень риска), фильтры, таблица; карточка изменения с объяснением — считается сразу при открытии |
| Проект → Pull request'ы | открытые PR с GitHub: «Оценить» одним нажатием или «Оценить все», подробности — по строке |
| Проверить изменение | проект → PR / коммит основной ветки / ветка — из выпадающих списков → «Оценить риск» |
| Очередь замеров | PR с метками cwv-risk в опрашиваемых репозиториях (живой опрос GitHub) |

Сторонние проекты — только прогноз: замер на стенде требует конфигурации сборки и сценария (`bench/repos/`).

```
cd system/web && npm install && npm run build      # фронтенд → web/dist
cd system
python -m cwv_risk web ingest                       # данные диссертации + замеры очереди → cwv-risk.db (~2 мин)
python -m cwv_risk web serve                        # http://127.0.0.1:8000 (API: /api/docs)
python -m cwv_risk web export --out web/static      # статическая копия (GitHub Pages, защита)
```

- Чтение — файлами `/api/*.json`: статическая копия — те же файлы на диске; действия (оценка, объяснение) —
  только у сервера. Маршрутизация через `#` — копия работает на GitHub Pages без настройки сервера.
- Опрашиваемые очереди — `system/web-config.json` (по умолчанию `sirpeperoni/bentopdf` → конфиг стенда `bentopdf`).
- Разработка фронтенда: `npm run dev` в `web/` (прокси `/api` → 127.0.0.1:8000).
- Прогноз для 4 проектов обучения не показывается (модель видела их коммиты); для 11 новых — прогноз модели
  отбора, сохранённый до замеров (`data/<проект>.scores.csv`).
